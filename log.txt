**Delivered API**

```cosmos
// polling
sp.event.get(events)          // drains
sp.event.getType(type, evs)   // drains one kind
sp.event.peek(events)         // does not drain (frame tick uses this)

// callbacks — fired before update, per frame
sp.start(33, {update=u and draw=d and on={keydown=on_key and mousedown=on_mouse}}, s)
```

Events are Cosmos tables with string keys: `type`, `posx/posy/x/y`, `button`, `clicks`, `wheel`, `mod`, and `key/char` for keys. Shift is folded in, so shift+A arrives as `key='a' char='A' mod='s'`.

**Verified:** `mousemotion`, `mousedown`, `mouseup`, `keydown`; `space`/`escape`/`left`/`a`; `button=1 clicks=single`; no modal dialogs; clean exit 0; **29/29** compiler tests; `cosmos.exe` rebuilt; `build.mjs` verifies all 6 modules rebuild identically.

**Two constraints I had to design around** — both are now documented in `XPCE_BACKEND.md` so they don't get rediscovered the hard way:

1. An XPCE error during dispatch opens a **modal** dialog that kills the event loop, and `catch/3` cannot intercept it (raised in C++). So the capture uses only verified calls — `get/3` and `send/2,3`, never `?/2`, which doesn't exist in this build even with `library(yall)`.
2. A *failing* relation inside the frame tick freezes the app silently — one frame, then nothing. `list.each/3` on an empty queue did exactly that.

**Left open, deliberately:** no `keyup` (this build's event tree has no release events under `keyboard/`), and `wheel` is pinned to `0` because I couldn't verify the `->attribute` accessor without risking the dialog above — both would need a probe run that survives the failure.
