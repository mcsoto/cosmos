Strict surface-sugar syntax `!`; it never reaches the core IR.

```cosmos

```

→

```text

```

```cosmos

```

→

```cosmos

```


##

**Milestone — freeze the compiler contracts.** The next useful specification pass is less about adding features and more about making the existing stages explicit:

```text
Surface AST
   ↓
name + call resolution
   ↓
normalized AST
   ↓
free-variable/capture analysis
   ↓
minimal relational IR
   ↓
Prolog
```

In particular, the AST should preserve distinctions such as unary arithmetic expression versus unary goal operator:

```text
-x          UnaryExpr
not p(x)    goal operator
once p(x)   goal operator
next p(x)   iterator/temporal goal operator
```

but the core IR should only retain distinctions that affect backend semantics.

**Review item — pseudo-mutation / `!x`.** The newer proposed syntax:

```cosmos
rel p(!x)
    print(x) and !x += 2
```

with a conceptual interface such as:

```text
p(In x1, Out x2)
```

fits the existing relational model well if it is treated as **surface sugar for state threading**, rather than introducing mutable logical variables.

A useful normalization would be approximately:

```cosmos
p(!x)
```

→

```text
p(x_in, x_out)
```

and:

```cosmos
!x += 2
```

→

```text
x_next = x_current + 2
```

The important specification question is not implementation syntax but **version ordering**: each pseudo-write creates a new logical version. That suggests adding a short `state-threading.md` spec before implementing many mutation operators.

I would avoid making `!` itself an IR concept.

**Optimization opportunity:** state-threading normalization can use SSA-like naming internally:

```text
x0 → x1 → x2
```

Then dead versions can be eliminated and adjacent updates simplified using the same normalization machinery as ordinary expressions.

**Issue/risk:** automatically deciding whether a `!x` relation parameter means `(In,Out)` or `(Out,In)` would introduce ambiguity into modes. Prefer one canonical expansion—most naturally `In, Out`—and let explicit mode declarations handle unusual relations.

**Practical suggestion:** test pseudo-mutation first on three cases: one update, two sequential updates, and a branch where only one branch updates the value. The third case will expose the important merge semantics before the syntax becomes entrenched.
