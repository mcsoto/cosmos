Space on XPCE

API reference and user guide for the Cosmos Space library, backed by SWI-Prolog's XPCE toolkit.

Overview

A native desktop canvas for Cosmos. It gives a program a real OS window with immediate-mode 2D drawing, a timer-driven game loop and an input event queue — no browser, no Electron, no network in the loop.

Library source

libs/space.co — the module you require('space', sp).

Implementation

libs/space_xpce.co (Cosmos wrapper) over libs/space_xpce_prolog.pl (raw Prolog/XPCE).

Compiled artifacts

space.pl + space.cif, space_xpce.pl + space_xpce.cif. Checked in; regenerate after editing either .co.

Worked examples

test4.co — an arrow-key rectangle. xpce/input.co — the input API: modifiers, callbacks, event queue.

Requirements

  • SWI-Prolog built with the XPCE toolkit. library(pce) and library(pce_main) must load, which on Windows also means the XPCE/SDL3 DLLs are reachable.
  • A --main, --xpce or --exe build (see Build & run). A bare compile cannot run.

Verify the toolkit before anything else:

?- use_module(library(pce)).
Not the same library

libs/xpce.co (require('xpce', xp), documented in XPCE_LIBRARY.md) is the raw toolkit: objects, messages, callbacks, event loop, no canvas. Reach for it when you want XPCE widgets; reach for space when you want to draw. Both are built the same way.

Quick start

A complete program needs two relations — update advances state, draw paints it — plus a window and a loop. Run it with:

cosmos -l quickstart.co --xpce
require('space', sp)

rel update(dt, s, s2)
    s2 = {x = s.x + dt * 120}          // 120 px per second

rel draw(s)
    g = sp.graphics
    g.clear(rgb(27, 27, 47))
    g.setColor(rgb(48, 80, 255))
    g.rectangle('fill', s.x, 100, 80, 50)

sp.init(640, 480)
sp.start(16, {update=update and draw=draw}, {x=100})

That is the whole program — no main relation, and require at the top of the file. --xpce is what makes this shape work; see below for why, and for the --main alternative if you want program arguments.

Build & run

The short way

cosmos -l test4.co --xpce

-l compiles a .co and runs it. --xpce picks the top-level-goals entry, which runs the file's own top-level goals instead of naming an entry relation.

The long way

Useful when you want the .pl or a standalone .exe instead of running straight from source.

$SWIPL = 'C:/Program Files/swipl/bin/swipl.exe'

# 1. Compile check only - no entry point, cannot be run.
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4

# 2. Runnable .pl with an argv entry point (needs a `main` relation).
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4 --main

# 2b. Same, but for a header-only program: --xpce instead of --main.
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4 --xpce

# 3. Standalone .exe - stages the XPCE DLL closure next to the binary.
& $SWIPL -q -s compiler/platform/cli.pl -- app.co app.exe app --main --exe
& app.exe                   # option 3, self-contained
swipl -q -s test4.pl          # options 2 and 2b
Option 1 does not run

The XPCE backend is not embedded — loading PCE at build time poisons a saved image — so it is loaded at runtime from a path recorded in the entry template, and that only happens for an entry shape. Build with --main, --xpce or --exe. The compiler adds the backend load on its own, by noticing that the output calls cosmos_require("space", _).

The loop model

sp.init(width, height)                 // size the window (created on start)
sp.start(intervalMs, callbacks, state)    // fixed interval, in milliseconds
sp.startCanvas(fps, callbacks, state)     // fixed frame rate, in frames/second

callbacks is a table with up to two loop entries, both optional:

KeySignatureCalled
updateupdate(dt, state, newState)once per frame, before drawing; binds newState
drawdraw(state)once per frame, with the state update produced

The same table may also hold the input callbacks — keypressed, keyreleased, mousepressed, mousereleased, mousemoved, wheel, textinput, focus, blur and resize. They are called with the arguments listed in Events, before update runs for that frame, and the state they produce is threaded through to update.

rel keypressed(key, state, newState)
    newState = state

sp.start(16, {update=update and draw=draw and keypressed=keypressed}, s)

Semantics that matter

  • dt is in seconds, not milliseconds, even though start takes milliseconds. It comes from get_time/1. Multiply your per-second rates by dt to stay frame-rate independent. It is also clamped to a few frame intervals, so a callback that took a long time — a long print, a slow disk write — cannot hand the next frame a huge step and make a game jump across the screen.
  • If update is omitted, state passes through unchanged. If draw is omitted, the frame is cleared and nothing is painted.
  • The window is cleared and flushed around draw, automatically. You do not call refresh. Clearing happens before draw using whatever background colour was last set, so g.clear('#202020') inside draw both paints and sets the background for subsequent frames.
  • An exception in update or draw is caught, printed as a warning, and the loop continues. A throwing callback will not stop the app; check stderr.
  • Closing the window quits, and so does sp.quit(); both halt the process. There is no need to stop a timer or destroy the picture — never try to close the window programmatically, it crashes the process outside the event loop.
  • One window per process. Every generated call passes an unbound prefix, which the backend resolves to default, so all Space state is shared. Calling init again resizes the existing window; two concurrent Spaces are not supported.

Events

Input arrives as callbacks into the backend and is queued here, PyGame-style. The queue is what sp.event operates on.

CallNotes
get(events)Drains everything delivered since the last call.
getType(type, events)Drains only events of one kind; the others stay queued.
peek(events)Does not drain. This is what the frame tick uses.
clear()Throws every pending event away without handing it over.
clearType(type)Throws the pending events of one type away; the rest stay queued.
has(type, found)found is 1 when an event of that type is waiting, 0 otherwise.
count(type, n)How many pending events of that type.
size(n)How many pending events in all.

The queue holds at most 256 events. A program that polls drains it every frame and never gets near the limit; a program that only uses the callbacks never drains it at all, and the oldest event is the one dropped when the queue overflows.

Each event is a table with at least a type field:

typeExtra fields
'mousemotion'posx posy x y dx dy button clicks mod
'mousedown'as above
'mouseup'as above
'mousewheel'as above, plus wheel (the scroll amount in notches)
'keydown'key char mod
'keyup'key mod — the release of the matching key-down
'textinput'text — the character a key press produced
'focus'the window gained the keyboard focus
'blur'the window lost it
'resize'width height

A field an event does not carry reads back as null rather than failing, so ev.posx on a keydown is harmless.

key is the lower-case name ('a', 'space', 'escape', 'left', 'f1'), char is the character as typed, and mod is any of "s" (shift), "c" (control), "m" (meta). Shift is already folded into the character, so shift+A arrives as key='a', char='A', mod='s'. A 'keyup' carries the same key name as the 'keydown' it ends.

dx and dy are the movement since the previous mouse event, so they are 0 on the first one the backend sees. clicks is the click count as XPCE reports it (single, double, triple), and button is the Space number: 1 left, 2 right, 3 middle.

rel update(_dt, s, s2)
    sp.event.get(events)
    list.each(events, show, _out)   // each/3 calls p(index, element, result)
    s2 = s
peek vs get

Every event reaches the callbacks exactly once — the tick fires the events the callbacks have not seen yet, not the whole queue — and the queue itself is only peeked at, so a polling program that drains with get() still finds the event. Using both styles in one program means seeing the event twice: once as a callback and once from the queue.

Callbacks (Love2D style)

There are two ways to be told about an event, and they work at the same time.

As a named callback

Put the relation under its own name in the sp.start table and the backend calls it for every event of that kind:

rel keypressed(key, state, newState)
    newState = state

sp.start(33, {update=update and draw=draw and keypressed=keypressed}, s)
CallbackArguments
keypressed(key, state, newState)the key name
keyreleased(key, state, newState)the key name
mousepressed(x, y, button, state, newState)
mousereleased(x, y, button, state, newState)
mousemoved(x, y, dx, dy, state, newState)dx/dy are the movement
wheel(dx, dy, state, newState)the scroll amount
textinput(text, state, newState)the typed text
focus(state, newState)
blur(state, newState)
resize(width, height, state, newState)

A callback that does not care about the state may leave the last two arguments out, and one that does not care about anything else may take only the leading ones. The state is threaded: a callback that produces a new state hands it to the next callback, and update runs with the state the input callbacks left behind.

The legacy names mousedown and mouseup are accepted as well; they get no button argument, because the old relations are (x, y, state, newState).

As an on table

Pass a table of per-type handlers instead, and the relation receives the whole event table:

rel on_keydown(ev)
    print(['key ', ev.key])

sp.start(33, {update=update and draw=draw and on={keydown=on_keydown}}, s)

Input & modifiers

Polling

sp.keyboard.isDown(key) polls XPCE's keyboard device, so it answers from the hardware and is correct even if the app missed a press or a release. The mouse side reads the state the event layer maintains, so the pointer only reports a real position after the first mouse event has arrived.

CallNotes
isDown(key)Succeeds while the named key is held. Under sp.keyboard and sp.input this is the keyboard.
isMouseDown(button)Succeeds while that button is held. Under sp.mouse, isDown/1 is the same thing.
getX(x) / getY(y) / getPosition(pos)Last known pointer position.
buttonDown(button)Succeeds while that button is held.

Key names are the lower-case Love2D ones — 'a', 'space', 'escape', 'return', 'tab', 'backspace', 'delete', 'left', 'right', 'up', 'down', 'home', 'end', 'pageup', 'pagedown', 'insert', 'pause', 'f1'…'f24' — and the DOM arrow aliases ('arrowleft', 'arrowup', …) are accepted as well. Mouse buttons may be given either as the number above or as the name 'left', 'right', 'middle'.

Modifier keys

NameSynonymsThe key
'shift'—either shift key
'ctrl''control'either control key
'alt''meta'either alt key
XPCE delivers no modifier events

XPCE's own manual says it: "a modifier key, such as Shift, generates neither" a key event nor a key release. So a program that only looks at the events never sees shift, control or alt being pressed. The backend therefore synthesises them: a modifier that goes down produces an ordinary 'keydown' event whose key is the modifier name, and letting go produces the matching 'keyup'. A modifier is thus visible both as an event and through isDown.

rel keypressed(key, state, newState)
    // key is 'shift', 'ctrl' or 'alt' for a modifier
    newState = state

rel update(dt, s, s2)
    sp.keyboard.isDown('shift', down)   // 1 while shift is held
    s2 = s

The mod field of any event carries the modifiers that were held when it happened, as the PyGame-style string "s", "c", "m" ("" for none).

There is no 'gui' modifier

XPCE's event mask has no bit for the GUI key, and the keyboard device of this build does not know the name of the key — asking about it raises Unknown key, and an XPCE error inside the event loop stops the frame for good. A modifier that cannot be seen is not offered at all, so 'gui' is not a name you can use.

The vocabulary stays XPCE-native

The SDL names ('Left Shift', 'Right Ctrl', …) are how the XPCE keyboard device spells those keys. They are used internally to talk to that device and are not part of the Space API. Arrows are the only alias exception, and they exist because the Space API has always documented both 'left' and 'arrowleft'.

API reference

Everything hangs off the sp table. sp.graphics, sp.input, sp.keyboard, sp.mouse, sp.timer and sp.event are sub-tables; input, keyboard and mouse are the same table under three names, matching the browser Canvas vocabulary. sp.input.isDown/1 is the keyboard, sp.input.isMouseDown/1 and sp.input.buttonDown/1 are the mouse.

Every method that takes a colour takes it in any of these forms:

The rgb(...) functor is exported by the library, so a program that requires 'space' can write it without declaring the functor itself. A component of 1 or less is a normalized value, a larger one is a byte; if any component is a byte, all of them are.

Drawing conventions

  • Colours are '#rrggbb' strings, [R,G,B] numeric lists, or the rgb(r,g,b) and rgba(r,g,b,a) functors the library exports. Anything else silently becomes white — a mistyped colour will not raise. A component of 1 or less is normalized, a larger one is a byte; if any component is a byte, all of them are.
  • Images are loaded by XPCE's image/1, so format support is XPCE's: GIF, JPEG and XPM work; PNG needs library(pce_image). A path that cannot be loaded is swallowed, so loadImage succeeds and draw then shows nothing.
  • Coordinates are pixels, rounded to integers; a non-number becomes 0. The origin is the top-left corner, y grows downward.
  • circle and ellipse take radii, whereas raw XPCE's circle/1 and ellipse/2 take a bounding-box size. This is the one place the API deliberately departs from XPCE so the numbers mean what they say.
  • newFont returns its result last, which is what lets g.setFont(g.newFont(24,'sans','normal')) work in value position.
  • Transforms apply to coordinates and to shape sizes, so scale inside a push/pop pair magnifies what you draw. shear is part of the same stack.

Compile-time checking

require('space', sp) is the supported entry point and is checked: arity and member existence are both enforced.

SourceResult
sp.init(320,480)accepted
sp.init(320)Wrong arity for sp.init
sp.graphics.clear('#fff')accepted
sp.graphics.clear(rgb(255,0,0))accepted
sp.graphics.clear()Wrong arity for sp.graphics.clear
sp.nosuch(1)Unknown imported member: sp.nosuch

Checking only happens when the interface sidecar is reachable, and the compiler looks for <name>.cif next to the file being compiled. misc/ has no space.cif, so the apps there are not checked. To check one:

Copy-Item libs\space.cif, libs\space_xpce.cif <your-dir>\

Arity and member existence are what get enforced. No parameter in the API carries a type annotation, so argument types are not checked today. Annotate space.co and space_xpce.co together or neither, or the two entry points will disagree about what compiles.

Keep the forwarding layer in step

libs/space.co is a forwarding layer over libs/space_xpce.co because re-exporting a required module directly does not work — the compiler records no members for it. See compiler_issue.txt. If you add a method to space_xpce.co, add a matching forwarder to space.co, or it stays invisible to anyone requiring 'space'.

Rules that will bite you

All three come from Cosmos language rules, not from this library.

  1. Match require's placement to the entry you build with. With --main, require goes inside the rel bodies: a top-level require captures the bound table into every relation, main/1 becomes main/2, and the argv adapter has to call it with that capture. With --xpce there is no main relation and the require goes at the top of the file, which is the whole point of that flag. Picking the wrong pairing is the usual reason a Space program opens a window and then does nothing.
  2. A relation's result is its last parameter. That is what makes newFont(size, family, style, font) usable in value position, and it is why getters take an out-parameter rather than returning a value.
  3. A functor crosses the pl:: bridge as fc_<name>. That is why the backend receives rgb(255,0,0) as the Prolog term fc_rgb(255,0,0), and why the backend accepts that term wherever a colour is expected. A program that requires a library which does not export the functor has to declare it itself before it can be used.
Not a bug

When require is at the top level, update and draw gain the captured sp as a trailing argument. The callback table stores them as closures, and call_cl/2 appends a closure's captures as the final argument, so the runtime's 3-argument update call still lands on the right predicate. Nothing to work around.

Limits

Known and deliberate for this version:

  • Keyboard state is polled, mouse state is event-driven. isDown/1 asks XPCE's keyboard device, so it is accurate at any time. buttonDown/1 and getX/getY/getPosition read the state the event layer maintains, so the pointer only reports a real position after the first mouse event arrives.
  • No 'gui' modifier. The event mask has no bit for it and the keyboard device of this build does not know the name of the key, so it cannot be offered.
  • setScissor records but does not clip.
  • setLineStyle records but does not change the pen — XPCE draws every line in one style. getLineStyle reads the recorded value back.
  • Rotating an ellipse moves its centre; the shape stays axis-aligned.
  • No window title control. The title is always Cosmos Space.
  • Image loading is format-limited and fails silently.
  • No overloading inside a table literal. Two rel with one name collapse, last one wins. That is why there is exactly one rel per method name.
  • No audio, no multiple windows, no z-order control.

Troubleshooting

SymptomCause
Unknown imported member: sp.…An interface .cif is reachable but stale, or you called a method that does not exist. Regenerate libs/*.cif, or remove the .cif beside your program to compile unchecked.
Unknown procedure: space_xpce_…The Prolog backend was never loaded. It is loaded at runtime from a path written into the entry template; a plain compile has no entry point and fails this way. Rebuild with --main or --xpce.
Window opens but nothing is drawnA draw/update exception is being swallowed as a warning. Read stderr.
A callback never firesIt must be registered in the sp.start table under its own name, and the argument list must match one of the documented forms.
Shift, control or alt never appearsThey are synthesised, so they arrive one frame late and only while the window has the focus. Check the modifier names: 'shift', 'ctrl', 'alt'.
Shapes have the wrong sizeYou passed a diameter where a radius is expected, or scale is still active from an unbalanced push.
A colour came out whiteThe value was neither '#rrggbb', [R,G,B] nor an rgb(...) / rgba(...) functor.
main/2 where you expected main/1A top-level require with a --main build. Move it into the rel bodies, or build with --xpce.
Process crashes on shutdownSomething tried to close or destroy the window from outside the event loop. Let process exit reclaim it.
