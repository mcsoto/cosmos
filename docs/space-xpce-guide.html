Space on XPCE

API reference and user guide for the Cosmos Space library, backed by SWI-Prolog's XPCE toolkit.

Overview

A native desktop canvas for Cosmos. It gives a program a real OS window with immediate-mode 2D drawing, a timer-driven game loop and an input event queue — no browser, no Electron, no network in the loop.

Library source

libs/space.co — the module you require('space', sp).

Implementation

libs/space_xpce.co (Cosmos wrapper) over libs/space_xpce_prolog.pl (raw Prolog/XPCE).

Compiled artifacts

space.pl + space.cif, space_xpce.pl + space_xpce.cif. Checked in; regenerate after editing either .co.

Worked example

test4.co — an arrow-key-controlled rectangle in the header-only shape.

Requirements

  • SWI-Prolog built with the XPCE toolkit. library(pce) and library(pce_main) must load, which on Windows also means the XPCE/SDL3 DLLs are reachable.
  • A --main, --xpce or --exe build (see Build & run). A bare compile cannot run.

Verify the toolkit before anything else:

?- use_module(library(pce)).
Not the same library

libs/xpce.co (require('xpce', xp), documented in XPCE_LIBRARY.md) is the raw toolkit: objects, messages, callbacks, event loop, no canvas. Reach for it when you want XPCE widgets; reach for space when you want to draw. Both are built the same way.

Quick start

A complete program needs two relations — update advances state, draw paints it — plus a window and a loop. Run it with:

cosmos -l quickstart.co --xpce
require('space', sp)

rel update(dt, s, s2)
    s2 = {x = s.x + dt * 120}          // 120 px per second

rel draw(s)
    g = sp.graphics
    g.clear('#1b1b2f')
    g.setColor('#3050ff')
    g.rectangle('fill', s.x, 100, 80, 50)

sp.init(640, 480)
sp.start(16, {update=update and draw=draw}, {x=100})

That is the whole program — no main relation, and require at the top of the file. --xpce is what makes this shape work; see below for why, and for the --main alternative if you want program arguments.

Build & run

The short way

cosmos -l test4.co --xpce

-l compiles a .co and runs it. --xpce picks the top-level-goals entry, which runs the file's own top-level goals instead of naming an entry relation.

The long way

Useful when you want the .pl or a standalone .exe instead of running straight from source.

$SWIPL = 'C:/Program Files/swipl/bin/swipl.exe'

# 1. Compile check only - no entry point, cannot be run.
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4

# 2. Runnable .pl with an argv entry point (needs a `main` relation).
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4 --main

# 2b. Same, but for a header-only program: --xpce instead of --main.
& $SWIPL -q -s compiler/platform/cli.pl -- test4.co test4.pl test4 --xpce

# 3. Standalone .exe - stages the XPCE DLL closure next to the binary.
& $SWIPL -q -s compiler/platform/cli.pl -- app.co app.exe app --main --exe
& app.exe                   # option 3, self-contained
swipl -q -s test4.pl          # options 2 and 2b
Option 1 does not run

The XPCE backend is not embedded — loading PCE at build time poisons a saved image — so it is loaded at runtime from a path recorded in the entry template, and that only happens for an entry shape. Build with --main, --xpce or --exe. The compiler adds the backend load on its own, by noticing that the output calls cosmos_require("space", _).

The loop model

sp.init(width, height)                 // size the window (created on start)
sp.start(intervalMs, callbacks, state)    // fixed interval, in milliseconds
sp.startCanvas(fps, callbacks, state)     // fixed frame rate, in frames/second

callbacks is a table with up to two entries, both optional:

KeySignatureCalled
updateupdate(dt, state, newState)once per frame, before drawing; binds newState
drawdraw(state)once per frame, with the state update produced

Semantics that matter

  • dt is in seconds, not milliseconds, even though start takes milliseconds. It comes from get_time/1. Multiply your per-second rates by dt to stay frame-rate independent.
  • If update is omitted, state passes through unchanged. If draw is omitted, the frame is cleared and nothing is painted.
  • The window is cleared and flushed around draw, automatically. You do not call refresh. Clearing happens before draw using whatever background colour was last set, so g.clear('#202020') inside draw both paints and sets the background for subsequent frames.
  • An exception in update or draw is caught, printed as a warning, and the loop continues. A throwing callback will not stop the app; check stderr.
  • Closing the window quits, and so does sp.quit(); both halt the process. There is no need to stop a timer or destroy the picture — never try to close the window programmatically, it crashes the process outside the event loop.
  • One window per process. Every generated call passes an unbound prefix, which the backend resolves to default, so all Space state is shared. Calling init again resizes the existing window; two concurrent Spaces are not supported.

Events

XPCE has no polling API in this build, so input arrives as callbacks into the backend and is queued here, PyGame-style.

CallNotes
get(events)Drains everything delivered since the last call.
getType(type, events)Drains only events of one kind.
peek(events)Does not drain. This is what the frame tick uses.

Each event is a table with at least a type field:

typeExtra fields
'mousemotion'posx posy x y button clicks mod
'mousedown'as above
'mouseup'as above
'mousewheel'as above, plus wheel (always 0)
'keydown'key char mod

A field an event does not carry reads back as null rather than failing, so ev.posx on a keydown is harmless.

key is the lower-case name ('a', 'space', 'escape', 'left', 'f1'), char is the character as typed, and mod is any of "s" (shift), "c" (control), "m" (meta). Shift is already folded into the character, so shift+A arrives as key='a', char='A', mod='s'.

rel update(_dt, s, s2)
    sp.event.get(events)
    list.each(events, show, _out)   // each/3 calls p(index, element, result)
    s2 = s
No keyup

This XPCE build's @event_tree has no release events under keyboard/, so only presses are ever delivered. A "move while held" model therefore has no way to know when to stop — nudge per press instead. Holding a key still glides, because the OS repeats the press.

Callbacks (Love2D style)

Pass an on table to sp.start and each event of that type is handed to the relation, before update runs for that frame:

rel on_keydown(ev)
    print(['key ', ev.key])

sp.start(33, {update=update and draw=draw and on={keydown=on_keydown}}, s)
peek vs get

The tick peeks at the queue for callbacks, so a polling program that drains with get() decides which frame sees which event. Pick one style per program.

Drawing conventions

  • Colours are '#rrggbb' strings or [R,G,B] numeric lists. Anything else silently becomes white — a mistyped colour will not raise.
  • Images are loaded by XPCE's image/1, so format support is XPCE's: GIF, JPEG and XPM work; PNG needs library(pce_image). A path that cannot be loaded is swallowed, so loadImage succeeds and draw then shows nothing.
  • Coordinates are pixels, rounded to integers; a non-number becomes 0. The origin is the top-left corner, y grows downward.
  • circle and ellipse take radii, whereas raw XPCE's circle/1 and ellipse/2 take a bounding-box size. This is the one place the API deliberately departs from XPCE so the numbers mean what they say.
  • newFont returns its result last, which is what lets g.setFont(g.newFont(24,'sans','normal')) work in value position.
  • Transforms apply to coordinates and to shape sizes, so scale inside a push/pop pair magnifies what you draw.

Compile-time checking

require('space', sp) is the supported entry point and is checked: arity and member existence are both enforced.

SourceResult
sp.init(320,480)accepted
sp.init(320)Wrong arity for sp.init
sp.graphics.clear('#fff')accepted
sp.graphics.clear()Wrong arity for sp.graphics.clear
sp.nosuch(1)Unknown imported member: sp.nosuch

Checking only happens when the interface sidecar is reachable, and the compiler looks for <name>.cif next to the file being compiled. misc/ has no space.cif, so the apps there are not checked. To check one:

Copy-Item libs\space.cif, libs\space_xpce.cif <your-dir>\

Arity and member existence are what get enforced. No parameter in the API carries a type annotation, so argument types are not checked today. Annotate space.co and space_xpce.co together or neither, or the two entry points will disagree about what compiles.

Keep the forwarding layer in step

libs/space.co is a forwarding layer over libs/space_xpce.co because re-exporting a required module directly does not work — the compiler records no members for it. See compiler_issue.txt. If you add a method to space_xpce.co, add a matching forwarder to space.co, or it stays invisible to anyone requiring 'space'.

Rules that will bite you

Both come from Cosmos language rules, not from this library.

  1. Match require's placement to the entry you build with. With --main, require goes inside the rel bodies: a top-level require captures the bound table into every relation, main/1 becomes main/2, and the argv adapter has to call it with that capture. With --xpce there is no main relation and the require goes at the top of the file, which is the whole point of that flag. Picking the wrong pairing is the usual reason a Space program opens a window and then does nothing.
  2. A relation's result is its last parameter. That is what makes newFont(size, family, style, font) usable in value position, and it is why getters take an out-parameter rather than returning a value.
Not a bug

When require is at the top level, update and draw gain the captured sp as a trailing argument. The callback table stores them as closures, and call_cl/2 appends a closure's captures as the final argument, so the runtime's 3-argument update call still lands on the right predicate. Nothing to work around.

Limits

Known and deliberate for this version.

  • Input arrives as events, not polling. sp.event.get() drains the queue and sp.input reads the state it maintains, so isDown/1, buttonDown/1 and getX/getY/getPosition only report real values after the first event arrives. There is no 'keyup', and wheel is always 0.
  • setScissor records but does not clip.
  • shear and setLineStyle are no-ops; getLineStyle-style accessors do not exist.
  • Rotating an ellipse moves its centre; the shape stays axis-aligned.
  • No window title control. The title is always Cosmos Space.
  • Image loading is format-limited and fails silently.
  • No overloading inside a table literal. Two rel with one name collapse, last one wins. That is why there is exactly one rel per method name.
  • No audio, no multiple windows, no z-order control.

Troubleshooting

SymptomCause
Unknown imported member: sp.…An interface .cif is reachable but stale, or you called a method that does not exist. Regenerate libs/*.cif, or remove the .cif beside your program to compile unchecked.
Unknown procedure: space_xpce_…The Prolog backend was never loaded. It is loaded at runtime from a path written into the entry template; a plain compile has no entry point and fails this way. Rebuild with --main or --xpce.
